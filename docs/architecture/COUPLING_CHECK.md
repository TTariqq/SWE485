**Required evidence (rubric):** the coupling detector flags the AI draft and clears the chosen option, and we explain a system-specific residual risk that the detector can't reveal.

> **Action for the team:** run the **course's official coupling detector** (from the M1 session instructions) on Draft 0 and on Option A, and save its report next to this file as `coupling_report_official.*`. The section below is our own reproducible check. It encodes the dependency graphs from [ARCHITECTURE_OPTIONS.md](ARCHITECTURE_OPTIONS.md) and checks four rules that come from [RULES.md](../../RULES.md).

## Rules checked

| Rule | Meaning | Why it matters here |
|---|---|---|
| R-C1 | No dependency cycles | A cycle between `blocks` and `bookings` means you can't change or test one without the other |
| R-C2 | The domain module has no outgoing dependencies | Booking rules can be unit-tested and mutation-tested without a web server or database (NFR-05) |
| R-C3 | At most one deployable unit writes to each datastore | Two programs writing the same tables share hidden assumptions about the schema |
| R-C4 | Only the persistence layer touches the datastore | SQL scattered in routes is hard to secure and to migrate |

**Instability:** `I = Ce / (Ca + Ce)`, where `Ca` (afferent coupling) is the number of modules that depend on this one and `Ce` (efferent coupling) is the number of modules this one depends on. `I = 0` means stable: nothing it depends on can break it. We want `domain` at `I = 0`.

## Residual risk the detector can't reveal

A passing structural check only shows that the *imports and connections* are clean. Our system has risks that live in **behaviour and shared assumptions**, which don't show up in a dependency graph:

**RR-1 Concurrency correctness depends on SQLite's runtime behaviour, not on structure.** Double-booking prevention (NFR-01) relies on two things working together: the partial unique index and the `BEGIN IMMEDIATE` transaction ([ADR-003](../adr/ADR-003-db-enforced-double-booking-prevention.md)). The coupling graph looks identical whether or not the transaction mode is set correctly. If someone removes `BEGIN IMMEDIATE`, or a migration forgets the `WHERE status = 'active'` part of the index, every coupling rule still passes, but:

- the per-student limits (FR-10, FR-11) can be bypassed by two simultaneous requests, or
- cancelled bookings block re-booking.

**How we detect it instead:**

- the 10-thread race test (100 runs) in the M2 suite;
- a schema test that asserts the index exists with the correct `WHERE` clause;
- the nightly integrity query (risk R1 threshold).

**RR-2 Hidden time coupling (secondary).** The domain, services and templates all assume "stored UTC, shown in Riyadh" ([ADR-004](../adr/ADR-004-utc-storage-and-injected-clock.md)). This is a *semantic* dependency with no import edge. One template that formats a UTC time without converting it shows every slot 3 hours early, and the coupling check stays green. **Detection:** SC-15 test and risk R6.
